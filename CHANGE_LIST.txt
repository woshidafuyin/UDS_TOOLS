二、功能变化
----------------------------------------

0. 奇瑞 E0Y Update_PublicKey 可选步骤

- 奇瑞 E0Y 目标配置新增 `Update_PublicKey` 复选框，语义与 CANoe Panel 一致，默认关闭；它不是独立刷写模式。
- 仅 APP 与 CAL 模式允许启用：完成 `27` 安全访问后、写 `2E F184` 指纹前，发送 `2E 6F00 + 514-byte public key`，并要求 ECU 返回 `6E 6F 00`。
- APP+CAL/TC_2 的原 CAPL 流程未使用该开关，界面会禁用并清除选择，流程层也会拒绝误配置。
- 514 字节载荷按 `FlashChery_E0Y_20240410/Capl/Flash.can` 固化；载荷 SHA-256 为 `517fb58290445bacca042a72594544eb64e5a41cd34a9e4a4e7243ea66e60762`。
- 已完成离线全量 CTest 8/8；尚未连接 CAN/ECU，实际写公钥与后续刷写仍需台架验证。

0. 可配置 APP 诊断端点贯穿正式刷写

- LP-ARF 已移除 APP `0x751/0x759` 的固定预检与流程规格耦合，界面配置的 APP Tx/Rx 贯穿预检、ISO-TP 和正式刷写；`0x701/0x761` 已取得一次 Vector XL + ECU 完整刷写成功证据。
- 吉利 P416/P417/P611 的 APP 通道改为使用当前 Profile Tx/Rx；SBL `0x716/0x616`、PLS `0x701/0x761` 和功能寻址仍保持独立协议约束，流程日志与 SBL 响应路由同步使用实际端点。
- 犀重 RSMR/LSMR 不再以默认 APP Tx/Rx 拒绝合法的 29 位自定义端点；RSMR/LSMR 身份、功能寻址、FT、NM、SeedKey 和 CAN FD/BRS 契约保持不变。
- 北汽 N61AB/BQB41 不再用 CANoe 默认端点白名单阻断合法的 11 位自定义 APP Tx/Rx；项目身份、帧格式、文件布局和安全访问约束保持不变。
- 新增共享的可配置诊断端点合法性校验及吉利端点路由对象，避免界面、探测、预检、流程规格和实际 ISO-TP 各自维护一套端点。
- 离线全量 CTest 8/8 通过；除 LP-ARF `0x701/0x761` 已有一次实刷成功外，吉利、犀重和北汽自定义端点仍需分别完成对应 ECU 台架验收。

0. 日志按用途分目录

- 界面运行日志写入 `logs/execution`，HTML 报告写入 `logs/reports`。
- 单次操作 Trace 统一进入 `logs/traces`，并按 `probe`、`version`、`diagnostic`、`flash` 分类；持续总线监听仍写入 `logs/bus_monitor`。
- 正式刷写每一轮同时保存同基名 ASC 和 Vector BLF，两种格式由同一批 `CanFrame` 同步写入，保留相同的帧数、方向、CAN ID、帧类型和 Payload。
- 重复刷写按完整轮次形成 `..._cycle_0001_of_0003.asc` / `..._cycle_0001_of_0003.blf` 成对证据，运行日志和 HTML 报告同时记录两个路径。
- 新增双写回归，覆盖经典 CAN、CAN FD/BRS、标准/扩展 ID、TX/RX 和 Payload；离线 CTest 8/8 通过，不代表真实 ECU 刷写或台架验收通过。
- “打开最新报告”和报告快捷按钮改为从 `logs/reports` 查找，不因目录调整失效。

0.1 移除错误的吉利 P146 项目

- 经项目确认，通用工具中不存在吉利 P146 项目，删除其 Profile、Workflow 注册、GEEA2.0 专用实现、运行资源和专项测试。
- 吉利下拉项目仅保留 P416、P417 和 P611；不再显示“P146（待补充）”。
- 原始客户项目测试工程资料不作为运行交付物，也不据此虚构 P146 产品能力。

0.2 吉利 P416 / P417 / P611 项目族

- 新增 `geely_p417.ini`、`geely_p611.ini`，在厂商“吉利”下提供 P416、P417、P611 / ARS1.31L 三个项目选择。
- P417、P611 完整复用 P416 的 CAN 配置、APP/PLS 双入口、SeedKey、版本读取 DID、服务顺序和 VBF 参数处理，不再保留 P611 ESS DFI 覆盖。
- 三个项目分别使用 `resources/geely_p416`、`resources/geely_p417`、`resources/geely_p611`；浏览选择刷写文件后，按原文件名原子复制到当前项目 Profile 的默认资源目录，保留默认文件、历史选择文件和外部源文件，项目间互不覆盖。
- 当前默认 ESS VBF 的 DFI 为 `0x00`，因此三个项目的 ESS `RequestDownload` 均为 `34 00 44 ...`。
- 已增加 Profile/独立资源、ESS DFI、默认资源替换、TX/RX 日志颜色和 Qt 项目切换回归；这些属于离线验证，不代表 P417/P611 真机刷写通过。

0.3 吉利 P416 VBF 选择与刷写

- 移除“仅允许成功 BLF 基线或 D:\JILI 精确组合”的 P416 文件内容哈希白名单。
- 移除 P416 专用的固定块数量、块地址/长度、擦除区、数据格式标识和固定签名长度阻断。
- 用户选择的 SBL、APP、ESS VBF 能够完成基础 VBF 解析后，按文件携带的数据块、擦除区、启动地址和签名进入现有刷写流程，由 ECU 实际响应决定结果。
- 仍保留读取 VBF 所必需的文件存在性、格式解析、截断和 CRC 完整性检查；损坏或无法解析的文件不会发送到 ECU。
- `D:\JILI\6608444966A.vbf`、`D:\JILI\12345_APP.vbf` 与ESS数据/签名相同的 `ess_out.VBF` 组合有P416成功BLF依据；本条结论不扩展到其他 ECU、入口模式或文件组合。

0.4 零跑 LP-ARF 6000/6001 非阻断响应处理

- `31 01 60 00` 和 `31 01 60 01` 仍按原顺序完整发送；允许空 Certificate 的跳过验签场景保持不变。
- 两个例程改为在有限窗口内接收、记录并消费肯定响应、最终 NRC 或无响应超时，但这些结果不判定刷写失败，也不阻止后续步骤。
- 收到 `NRC 0x78` 时进入一次性、受限的 P2* 观察窗口，避免无限等待；最终响应仍只记录并消费。
- 请求本身的 ISO-TP 发送、FlowControl 或报文组装失败仍属于传输失败，不会被“跳过验签”策略掩盖。
- 修复迟到的 `7F 31 13` 残留在接收队列、随后被 `2E F1 98` 误判为 FlowControl 并报 `ISO-TP flow control rejected` 的问题。
- 新增肯定响应、最终 NRC、无响应、`NRC 0x78` 后最终响应，以及 `6000` NRC 不污染后续多帧 `F198` 的离线回归测试；全部 8 项 CTest 通过。真实 ECU 刷写仍需台架复验。

0.5 零跑 LP-ARC / LP-ARF 恢复CANoe正常流程严格验签

- 本条取代0.4中的LP-ARF非阻断策略：LP-ARC和LP-ARF均不再允许空Certificate进入刷写流程。
- LP-ARC恢复Profile默认1322字节ASC；LP-ARF的TMP必须内置1322字节Certificate，S19/SREC/BIN必须搭配1322字节ASC或TMP验签文件。
- 两个项目均依次发送`31 01 60 00 + Certificate`和`31 01 60 01`，严格要求`71 01 60 00 04`和`71 01 60 01 04`肯定响应。
- `6000/6001`收到NRC、超时或状态不符立即终止，不再采用observe-and-continue；ISO-TP发送和FlowControl失败仍按传输失败处理。
- 本次对齐CANoe正常`Download()`流程，不把CANoe故障注入、跳步或数据破坏Test Case暴露为交付刷写功能；真实ECU一致性仍需同硬件、同文件A/B台架复验。

0.6 零跑验签文件改为可选并采用CANoe Skip语义

- 本条调整0.5的文件门禁：LP-ARC和LP-ARF均不强制用户添加验签文件。
- 提供Certificate时仍要求恰好1322字节，依次发送`31 01 60 00 + Certificate`和`31 01 60 01`，并严格判定两个预期肯定响应。
- 未提供Certificate时按CANoe Skip控制同时省略`6000/6001`，直接进入`2E F198`及后续流程；不发送空Certificate，也不采用非阻断响应观察。
- LP-ARF选择TMP且包内含Certificate时自动执行严格验签；选择S19/SREC/BIN时可搭配ASC/TMP，也可不选择并走Skip。
- 增加Profile默认空验签、可选UI、严格/Skip双策略和APP-only输入回归；真实ECU对Skip路径的接受程度仍需台架验证。

1. 新增“诊断报文”页

- 自动跟随刷写作业当前项目、目标、CAN 后端、通道、波特率、CAN FD、物理 Tx/Rx ID、功能 ID、Padding 和 ISO-TP 参数。
- 支持物理/功能寻址的单次 UDS 请求，显示完整响应、耗时、错误和 NRC，并保存独立 ASC Trace。
- 与探测、刷写、版本读取和电源操作共用操作互斥门禁；状态改变类服务发送前二次确认。
- 不提供任意原始 CAN、周期发送或自动安全解锁，不把单报文工具误用为项目恢复 Workflow。

2. 总线监听 Trace 和过滤

- 工具启动后自动被动监听当前刷写通道，无需手工点击开始。
- 完整 Trace 改为自动录制 Vector BLF，持续写入 `logs/bus_monitor`，不受 UI 最近 10,000 帧缓存限制；探测、版本读取、诊断和刷写的单次 Trace 仍保持 ASC。
- BLF 同时保留经典 CAN、CAN FD/BRS、标准/扩展 ID、通道、TX/RX、时间戳和完整 Payload；实现位于通用 CanFrame/Trace 边界，不耦合特定硬件厂商。
- 运行中使用 `.blf.partial`，正常结束形成 `.blf`；异常恢复按 BLF 文件头最后提交的完整容器大小截断损坏尾部，历史 `.asc.partial` 仍兼容恢复。
- “导出 BLF”导出完整磁盘 Trace，而不是只导出当前表格缓存。
- 支持诊断 ID 精确值、范围、掩码和排除过滤。
- 增加当前项目诊断 ID、功能寻址、物理寻址和周期帧快捷过滤。
- 区分总接收、当前显示和内存淘汰帧数。
- 修正 NRC 识别，避免把 Seed、签名或刷写数据中的 7F 误判为负响应。

3. 监听完整跟随 CAN 硬件上下文

- 监听上下文包含硬件后端、物理通道、仲裁/数据波特率和 CAN/CAN FD。
- 监听页显示 Vector、ZLG、TOSUN、Kvaser 等当前后端和通道。
- 切换项目、目标、后端或通道后自动释放旧监听并在新上下文恢复。
- 探测、读取和刷写前检查监听上下文与当前配置一致；无法对齐时失败关闭。
- 被动监听不发送任何 CAN/UDS 报文。

4. ZLG 零发送后的共享通道恢复

- 独立识别“适配器确认发送 0 帧”的错误，并保留底层通道错误信息。
- 单帧明确发送 0 帧时关闭并重建共享通道，然后安全重试一次。
- 只有确认发送成功后才发布 TX 记录。
- 多帧或部分发送状态不确定时不整批自动重放，避免重复 UDS 服务或刷写数据。

5. 刷写资格和完整配置审计

- 记录最近一次“能否刷写”的结果、完成时间和配置指纹。
- 探测后改变配置会标记 STALE_CONFIG，不把旧结果当成当前配置证明。
- 记录硬件后端、通道、Tx/Rx ID、仲裁/数据波特率、CAN FD、Padding 和入口模式。
- 记录 Driver、校验、APP、CAL、SeedKey 等文件路径、存在性和大小。
- 审计信息同时进入运行日志和 HTML 报告。

6. 目标身份审计

- 记录厂商、项目、设备显示名、Profile ID、Target ID 和 Flow ID。
- 记录入口模式和刷写重复次数。
- 目标显示名与 Profile、Target、Tx/Rx ID 组合记录，避免仅凭中文名称判断 ECU。

7. 执行日志持续尾随

- 按 End 后跳到当前末尾并进入持续尾随模式。
- 后续日志到达后继续滚动到最新末尾。
- 按 Home 或向上滚动阅读历史时暂停尾随。
- 再次按 End 或滚到底部后恢复尾随。
- 版本读取进度仅显示在状态栏，不再覆盖刷写页最近一次刷写结果文字。
- 版本读取开始、成功、失败或停止均写入清晰分隔标记；失败只追加记录，不清除此前刷写日志。
