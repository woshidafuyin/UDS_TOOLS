三、新增和改进功能
----------------------------------------

1. 总线监听 Trace 和过滤能力
对应提交：9f54b2f

- 总线完整 Trace 持续写盘，不再受 UI 表格内存上限限制。
- 运行中使用 .partial Trace；正常停止后形成完整 ASC。
- 支持发现和恢复未正常结束的 Trace。
- 导出完整 Trace，而不是只导出 UI 当前缓存。
- 增加诊断 ID 精确值、范围、掩码和排除过滤。
- 增加当前项目诊断 ID、功能寻址、物理寻址和周期帧快捷过滤。
- 区分总接收帧数、当前显示帧数和内存淘汰帧数。
- UI 仅保留有界帧缓存，完整证据由 Trace 文件承担，降低长期监听的内存风险。
- 修正 NRC 识别：仅把 RX UDS Payload 起始位置的 7F 识别为负响应，避免把 Seed、签名或刷写数据中的 7F 误报为 NRC。
- 用户可见程序名统一为 UDS_Tool.exe。

2. 被动监听完整跟随 CAN 硬件后端
对应提交：a09ee6a

- 监听上下文从“通道和波特率”扩展为“硬件后端、通道、波特率、CAN/CAN FD”的完整上下文。
- 监听页明确显示 Vector、ZLG、TOSUN、Kvaser 等当前 CAN 后端及通道。
- 切换 CAN 后端时停止旧监听、释放旧通道、恢复新后端的通道配置并重新监听。
- 项目、目标、后端或通道变化时同步版本读取页和总线监听页。
- 在线探测、版本读取和刷写执行前检查监听上下文是否与当前配置一致；无法对齐时失败关闭，避免在错误后端上继续执行。
- 被动监听期间仍允许切换后端；只有实际探测、读取或刷写操作期间才锁定相关配置。

3. ZLG 发送 0 帧后的共享通道恢复
对应提交：2f8f386

- 新增“适配器确认发送 0 帧”的独立错误分类，并保留 ZLG 通道错误信息。
- 单帧明确发送 0 帧时，主程序关闭并重建共享 CAN 通道，然后安全重试一次。
- 只有确认发送成功后才把该帧发布为 TX 记录。
- 对多帧或部分发送状态不确定的批次禁止整批自动重放，避免重复发送 UDS 服务或刷写数据。
- 多帧失败后重置通道，为用户下一次明确发起的操作恢复通道条件。

注意：tools\can_hardware_probe.exe 已随 CAN 适配层重新构建并获得更明确的错误分类；主程序 Shared CAN Provider 的“重建并重试”不能等同为独立硬件探针的完整行为。

4. 刷写前资格和完整配置审计
对应提交：816998d

- 记录最近一次“能否刷写/在线探测”的状态、结果和完成时间。
- 比较探测时配置与当前刷写配置；不一致时记录 STALE_CONFIG。
- 记录硬件后端、CAN 通道、Tx/Rx ID、仲裁/数据波特率、CAN FD、Padding 和入口模式。
- 记录 Driver、Driver 校验、APP、APP 校验、CAL、SeedKey 等文件路径。
- 记录刷写文件是否存在及文件大小。
- 上述内容同时进入运行日志和 HTML 报告。
- 审计只增加可追溯证据，不绕过 Profile/Workflow 的刷写前置检查。

5. 刷写目标身份审计
对应提交：20eef97

- 记录厂商、项目、设备名称。
- 记录 Profile ID、Target ID 和 Flow ID。
- 记录入口模式和刷写重复次数。
- 与硬件后端、通道、诊断 ID 和刷写文件审计组合，形成一次刷写的完整配置快照。

已知限制：目标中文显示名必须同时与 Profile ID、Target ID 和 Tx/Rx ID 核对，不能只依赖显示名判断实际 ECU。

6. 执行日志 End 键持续尾随
对应提交：0b94ac8

- 按 End 后不仅跳到当前末尾，还进入持续尾随模式。
- 后续刷写日志到达时继续自动滚动到真正的最新末尾。
- 用户按 Home 或向上滚动查看历史时暂停自动尾随，避免抢走阅读位置。
- 用户再次滚到底部或按 End 后恢复持续尾随。
- 使用延迟到 UI 文档布局完成后的滚动处理，解决“只到达按键时的旧末尾”问题。
