# 楚能 331 刷写流程对比：规范 vs LP 参考 vs 实测（2026-08-19）

依据：
- 楚能规范：Q/CN A201-2025《BootloaderOnCAN(FD)刷新规范》（规范目录提取文本）
- LP/CANoe 参考：`LP_ARC331\ARC`（Flash20230727.can）及 Logging 实机 BLF
  （7-15/8-17/8-18 成功记录，均解析自 `scripts\scan_blf_logging.py` /
  `scripts\analyze_blf_summary.py`）
- 实测：本工具连板（楚能 LeRR ECU，F197=`LeRR`，会话 `00 32 01 5E`，
  0x72E/0x72F，CH2）多次刷写结果

## 一、Q/CN A201-2025 规范 vs LP（CANoe）流程对比

| 步骤 | 楚能规范 Q/CN A201-2025 | LP/CANoe 参考（7-15/8-17/8-18 实机成功） |
|---|---|---|
| 预编程 | 物理 `10 03` → 物理 `31 01 02 03`（0x04 通过）→ 功能 `10 83`/`85 82`/`28 83 03` | 功能 `10 01` → 物理 `22 F197/F150/F189`（读 DID）→ 功能 `10 03`/`85 02`/`28 03 01` |
| 编程会话 | 物理 `10 02` | 物理 `10 02`（相同） |
| 私有握手 | 无 | **`0x771 FB A5 00`**（27 11 之前，8-17/8-18 均有） |
| SeedKey | 16 字节种子/密钥 | 4 字节种子/密钥（LP DLL） |
| 证书例程 | **无 6000/6001** | `31 01 60 00`（1322B 证书）→ `31 01 60 01`（版本） |
| 序列号/指纹 | 无 F198；`2E F1 84`（9 字节指纹，在 0301 激活 SBL 后） | `2E F1 98`（19B 序列号）→ `2E F1 99`（4B BCD 日期指纹，6001 后） |
| Driver 下载 | `34/36/37`（0x802 块） | `34/36/37`（0x802 块，相同） |
| Driver 校验 | `31 01 02 02` + **256 字节签名**（4.5.4） | `31 01 02 02` + **4 字节 CRC32**（如 `85 09 E3 88`）→ 0x04 |
| 激活 SBL | `31 01 03 01` | **无 0301**（LP 流程没有） |
| APP 擦除 | `31 01 FF 00` | `31 01 FF 00`（相同） |
| APP 下载 | `34/36/37` | `34/36/37`（相同） |
| APP 校验 | `31 01 02 02` + 256 字节签名 | **无 APP 0202**（APP 后直接 0203/FF01） |
| 条件检查位置 | 预编程阶段（0203，0x04） | **APP 下载后** `31 01 02 03` → 0x04（7-15 实机） |
| 兼容检查 | `31 01 FF 01` | `31 01 FF 01`（相同） |
| 复位 | `11 01` | `11 01`（相同） |
| 后编程 | 功能 `10 83`/`85 81`/`28 80 03`/`10 81`/`14 FF FF FF` | 功能 `10 03`/`28 00 01`/`85 01`/`14 FF FF FF`/`10 01` |

结论：**LP/CANoe 流程是零跑/宝腾（perodua Q01A）移植模板**（Download_File.Ini
路径为 `D:\Project\perodua\Q01A\...`、`D:\Project\lingpao\ARC331\...`），
与楚能规范在证书例程、密钥长度、0202 参数、指纹 DID、0301 激活 SBL、
0203 位置等多处不同。

## 二、本工具实测结果（楚能 LeRR ECU）

| 步骤 | 结果 |
|---|---|
| 探测/10 03 | ✓ 在线，`50 03 00 32 01 5E` |
| `31 01 02 03` 条件检查 | **0x05（不满足）**，已 WARN 容错继续 |
| `10 02` 编程会话 | ✓ |
| `27 11/27 12`（16 字节） | ✓ 安全访问通过（楚能 DLL） |
| Driver 34/36/37（0x802 块） | ✓ 下载完成 |
| `31 01 02 02`（CBF 256B 签名） | **0x05 校验失败** |
| `31 01 02 02`（4B CRC32 实验） | **NRC 0x13 长度错误** |
| `31 01 02 02`（S19 DriverVerification.asc 256B） | **0x05 校验失败** |
| `31 01 60 00`（旧 LP 流程） | **NRC 0x31 例程不支持**（16:03/16:15 历史记录） |

关键推断：
1. LeRR ECU **按楚能规范实现**：无 6000/6001（NRC 31）、16 字节 SeedKey、
   0202 期望 256 字节参数（4B → NRC 13）。
2. **两种 Driver 组合的 0202 均 0x05**：
   - `FlashDriver.srec` + `DriverVerification.asc`（CANoe 台架 LP ECU 配套）
   - CBF `driver_712345678AB.cbf` main + dev_signature
   即：**当前板子 Boot 信任的 FlashDriver 不是这两套**（规范 5.4.3.4：
   0202 不通过 = 下载的驱动代码与该 Bootloader 不对应）。
3. 数据事实：`FlashDriver.srec` CRC32=`8509E388`；CBF Driver main
   CRC32=`F8B218E9`（两者内容不同）；S19 APP（CHF0330N）CRC32=`F8108BEE`；
   CBF APP main CRC32=`5C587678`（两者内容不同）。CBF 套件
   （7052A5023002AB）与 S19 套件（CHF0330N）是**两套不同软件**。

## 三、需要与同事/供应商确认的问题（按优先级）

1. **当前板子（LeRR，会话 00 32 01 5E）Boot 配套的 FlashDriver 是哪个文件？
   它的 256 字节签名（ASC/CBF dev_signature）是哪个？**
   —— 这是当前唯一阻塞点（0202 0x05）。
2. **Driver 0202 的 256 字节签名是否必须与"下载的 Driver 数据"配套**，
   还是 ECU 只校验 Driver 与 Boot 的版本匹配（不看我们传的参数）？
3. **APP 用哪套**：CHF0330N（S19 套件）/ 7052A5023002AB（CBF 套件）/
   CHF0389N（最新 712345678AA CBF，规范包 1\ 目录）？
4. **0203 条件检查在裸板台架返回 0x05**：确认台架刷写时是否可以跳过
   （本工具已 WARN 容错继续）；整车环境应返回 0x04。
5. **是否遵循楚能规范流程**（无 6000/6001、0202 256B 签名、0301+F184、
   16 字节密钥）——本工具已按规范实现，仅卡在 Driver 签名配套。

## 四、本工具当前流程（实测到 0202）

```
物理10 03 → 物理31 01 02 03(0x05→WARN继续) → 功能10 83/85 82/28 83 03
→ 物理10 02 → 27 11/27 12(16B) → 2E F1 84指纹? → Driver 34/36/37

```
